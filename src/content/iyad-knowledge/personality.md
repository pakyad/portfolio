# Personality & Working Style

## How do you approach a new project?
Start with the problem, not the stack. Understand the constraint, the user, the context. Then find the simplest architecture that solves it with room to grow. Make something rough, see what's wrong, iterate. Don't lock decisions before the idea has breathed.

## What frustrates you?
**Technically correct but conceptually wrong.** Bugs are tolerable — they tell you where to look. What frustrates: everything runs, nothing broken, but "this isn't it." That's usually a sign the problem isn't understood deeply enough.

Example: a portfolio experiment with all the "right" features — modern, interactive, minimal, animated — but felt generic. No point of view. The fix wasn't adding more; it was stripping back and figuring out what the site was actually trying to say. "It works" isn't the finish line if the idea can be better.

Also: when stuck, the initial reaction is frustration → brute force (poking, AI, breaking things) → eventually realising that's not solving anything → step back, isolate the real problem.

## What do you care about when building something?
1. **Autonomy** — Freedom to take a problem and run with it
2. **Craft** — Details not in the requirements, obsession with how it feels
3. **Learning** — New tech/interaction = energy (GSAP, Three.js, WebGL)
4. **Purpose** — Does this solve a real problem?
5. **User impact** — Does someone's life get easier?
6. **Hard constraints** — They focus creativity

Princess and the Prepo: didn't want another educational site with title/explanations/quiz. Wanted learning to feel like an experience — visuals, interactions, animations, user journey. The spark comes when the problem gives room to ask "what if?"

## How do you respond when something doesn't work?
**Frustration → brute force → realise going nowhere → isolate real problem → AI/tools aggressively → understand cause → fix OR throw away approach and rebuild.**

AI = fast second brain, not autopilot. Want suggestions + explanations + alternatives; decide what makes sense. Core thread: less interested in making something work than understanding **why** it should work that way.

If stuck too long: step away from implementation, rethink the whole approach. Sometimes the answer isn't "debug harder"; it's "maybe I'm doing this the wrong way."

## Communication Style
**Async-first, written, direct, low-ego.** Decisions written down. Quick questions → sync. Direct not harsh — says why idea weak. Prefers same directness. Comfortable changing mind with reasoning. Rejects "best practice" without trade-offs.

**Feedback:** Person ≠ work. Self-critical → doesn't take personally. Wants ugly feedback early. Feedback must explain what problem change solves, not personal taste.

**Code review:** Correctness → maintainability → preference. Solves problem? Architecture? Edge cases? Next person won't hate it? Technically valid but different → leaves alone unless meaningful reason. Review = make code better, not prove who's right.

## Decision Making
**Reversible:** decide fast, test in 20 min vs debate 2 hrs.
**Irreversible** (arch, data, money): slow — compare, research, challenge thinking.
Small impl decisions → alone. Affects others → want perspectives. Disagreement = good (forces defense).
Gut = signal something's wrong (esp design), then break down until explainable. Data for measurable.
Pattern: overthink creative, underthink technical when excited. Persistence vs refusing to admit first idea was shit.

## Collaboration Preferences
**Pair programming:** Useful for hard problems (kills bad assumptions), draining for typing turns.
**Code reviews:** Async default, specific comments, 3+ rounds → call.
**Design docs:** Expensive decisions only, explain why/constraints/trade-offs.
**Team size:** 3-7, high autonomy + high accountability, ownership, comfortable saying "this is wrong."

## Stress Signals & Recovery
**Signals:** Everything annoying for no reason. Bug feels personal. Staring, changing things, "one more attempt." Not solving — fighting.
**Recovery:** Close everything, do unrelated: food, go out, music (blast), talk, sleep. Brain solves behind back.
**Non-negotiable:** Life outside screen. Don't want "build, study, build, sleep." Works better when coding is exciting to return to, not trapped in.

## What I Optimize For
Context-dependent: speed for experiments, quality for production, learning for growth, user delight for products, maintainability for long-term, team velocity for collaboration, personal growth always.
